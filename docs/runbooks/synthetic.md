# Synthetic checks

This runbook is where the `runbook_url` on a **synthetic-check** alert lands. For each service that
declares an `alerts:` binding and renders a Gatus ingress check (it has an `ingress_url` and is not
suppressed), the alerting transform emits **one critical `GatusCheckFailed` rule** over Gatus's own
`gatus_results_total` counter.

This is the **outside-in** signal: "a blackbox request to the service's public URL keeps failing."
It is distinct from **host liveness** (`HostDown`, in the [availability runbook](/availability/)) and
from the service's **declared functional health** ([deep health](/deep-health/)). If `HostDown`
fires for the same host, start there: a dead host explains a failing check.

The rule is generated by `stack/alerting/src/transform/synthetic-rules.ts`; the slug comes from
`RUNBOOK_SLUGS.synthetic` in `stack/alerting/src/constants.ts`. The endpoint name is
`<host>/<service>`, the same name Gatus shows for the check.

## When this fires

- **GatusCheckFailed** (critical) — every Gatus check of the service's ingress URL in the last
  `failure_threshold` minutes failed (default 3; Gatus checks run every 60s), with no passing check
  in that window. Labels: `endpoint` (`<host>/<service>`), `group` (the host), `source: gatus`.
  Annotations: `url` (the checked URL) and, when the binding sets one, `description`.
- It resolves `success_threshold − 1` minutes after the first passing check (default 1 minute,
  via `keep_firing_for`). While the check keeps failing, vmalert keeps re-sending the alert, so it
  stays firing for the whole outage.

## Triage

**Verify (content):** confirm the rule's input series is live, so the alert is not reading stale
data. From the engine host:

```bash
cd stack/compose
docker compose run --rm --entrypoint sh alertmanager -c \
  "wget -qO- 'http://victoriametrics:8428/api/v1/query?query=sum%20by%20(name%2Ckey%2Csuccess)%20(increase(gatus_results_total%7Bname%3D%22HOST%2FSERVICE%22%7D%5B5m%5D))'"
```

Replace `HOST%2FSERVICE` with the alert's `endpoint` label (`/` URL-encoded as `%2F`). A
`success="false"` value above 0 and no `success="true"` increase confirm the failure is current.
Note the `key` label for the next step. If the query returns nothing at all, Gatus is not being
scraped. Check `up{job="gatus"}` and the `AncillaryDown` alert in the [engine runbook](/engine/). A
Gatus outage silences this rule rather than firing it.

**Verify (content):** read what Gatus itself saw on the recent checks, using the `key` from the
previous query:

```bash
docker compose run --rm --entrypoint sh alertmanager -c \
  "wget -qO- http://gatus:8080/api/v1/endpoints/KEY/statuses" | head -c 2000
```

The recent `results` show `success: false` with the failing condition (for example
`[STATUS] (503) == 200`) or a connection error. That tells you whether the service answers badly or
not at all.

**Verify (content):** reproduce the check from outside Gatus. From any host that has the same
network path as the engine:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://SERVICE.example/
```

A non-200 code or a connection error matches the alert. A `200` here while Gatus keeps failing
points at the engine's network path (DNS, routing, TLS trust), not the service.

## Remediate

#### Step 1 — Restore the service behind the ingress URL

Act on what triage showed: bring the service or its reverse proxy back, renew an expired
certificate, or fix the DNS record the URL resolves through. This happens on or against the
**monitored service**, not the engine.

**Command**

```bash
# On the service host — example shape; the real action is whatever makes the URL answer 200 again.
docker compose -f /path/to/service/compose.yml restart SERVICE
```

**Verify (content):** the Gatus statuses query above shows new `success: true` results for the
endpoint, and the alert clears about `success_threshold − 1` minutes after the first pass. Judge by
the check results, never by the restart's exit code.

**Rollback:** none — restoring the service has no state to undo. If your action made things worse,
revert it on the host (re-pin the prior image, or `git checkout` the service compose) and re-up.

#### Step 2 — If the check or thresholds are wrong, re-declare and re-render

If the service is genuinely healthy and the check is mis-specified (wrong `ingress_url`, a URL
that legitimately answers non-200, or a threshold too tight for a service that blips), fix it in the
estate and re-render rather than muting the alert. Tune `failure_threshold` / `success_threshold`
on the service's `alerts:` binding, or set `enabled: false` to stop paging on that check.

**Command**

```bash
# Edit the service's ingress_url or alerts: binding in the estate, then:
( cd examples/reference && "$PULSE_BIN" render )
bun run alerting:render examples/reference/estate examples/reference/rendered
```

**Verify (content):** the regenerated rule reflects the change. Run
`grep -B2 -A12 'endpoint: HOST/SERVICE' examples/reference/rendered/vmalert/rules/synthetic.yml` and
check the `[Nm]` window in `expr` (failure threshold in minutes) and `keep_firing_for`. With
`enabled: false` the rule is gone. Reload vmalert and confirm the rule no longer fires against a
healthy check.

**Rollback:** `git checkout -- examples/reference/` restores the prior estate and rendered rules.
